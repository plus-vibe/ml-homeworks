# DS Infrastructure Homework

Учебный Python-проект по инфраструктуре ML и подготовке данных.

Проект объединяет два домашних задания:

- **ДЗ №1 — Инфраструктура проекта:** управление зависимостями, проверки качества кода, pre-commit, Git и CI.
- **ДЗ №2 — Данные и S3:** локальное S3-хранилище RustFS, загрузка CIFAR-10, конвертация, разбиение, статистики и версионирование датасета.

## Технологии

- Python 3.12
- uv — управление зависимостями
- Ruff — линтер и форматтер
- mypy — статическая проверка типов
- pre-commit — проверки перед коммитом
- GitHub Actions — CI для pull request
- Docker Compose — управление контейнерами
- RustFS — локальное S3-совместимое хранилище
- boto3 — работа с S3
- NumPy и Pillow — обработка изображений

## Требования

- Linux или Windows с WSL2 (Ubuntu)
- Git
- Make
- curl
- Docker с поддержкой Docker Compose
- Доступ к интернету для первоначальной установки

Python и зависимости проекта устанавливаются через uv.

## Быстрый старт

### 1. Клонирование репозитория

```bash
git clone git@github.com:plus-vibe/ml-homeworks.git
cd ml-homeworks
```

### 2. Подготовка окружения

```bash
make setup
```

Команда использует установленный uv или пытается установить его автоматически, если он отсутствует.

После этого создаётся виртуальное окружение, устанавливаются зависимости из `uv.lock` и подключаются Git-хуки pre-commit.

### 3. Настройка S3

Создайте локальный файл конфигурации:

```bash
cp .env.example .env
```

Заполните переменные в `.env`:

| Переменная | Назначение |
|---|---|
| `RUSTFS_ACCESS_KEY` | Ключ доступа к RustFS |
| `RUSTFS_SECRET_KEY` | Секретный ключ доступа |
| `S3_ENDPOINT_URL` | Адрес S3 API |
| `S3_BUCKET` | Название бакета |
| `S3_API_PORT` | Порт S3 API |
| `S3_CONSOLE_PORT` | Порт веб-консоли |

Для локальной разработки используется endpoint:

```text
http://localhost:9000
```

Файл `.env` содержит секреты и не должен попадать в Git. В репозитории хранится только `.env.example`.

### 4. Запуск S3

```bash
make s3-up
```

Команда запускает RustFS через Docker Compose, ожидает готовности сервиса и выполняет инициализацию бакета.

Веб-консоль RustFS доступна по адресу:

```text
http://localhost:9001
```

Проверить состояние контейнеров:

```bash
make s3-status
```

Остановить сервис:

```bash
make s3-down
```

При обычной остановке named volume сохраняется, поэтому данные не удаляются.

## Dataset Card: CIFAR-10

### Общая информация

| Характеристика | Значение |
|---|---|
| Название | CIFAR-10 |
| Источник | University of Toronto |
| Назначение | Классификация изображений |
| Всего изображений | 60 000 |
| Размер изображения | 32 × 32 пикселя |
| Цветовое пространство | RGB |
| Количество классов | 10 |
| Исходный формат | Python batches в tar.gz |
| Обработанный формат | PNG + JSON |
| Версия обработанных данных | v1 |

Официальная страница датасета:

https://www.cs.toronto.edu/~kriz/cifar.html

Исходный архив:

https://www.cs.toronto.edu/~kriz/cifar-10-python.tar.gz

### Классы

1. airplane
2. automobile
3. bird
4. cat
5. deer
6. dog
7. frog
8. horse
9. ship
10. truck

### Разбиение данных

Исходный CIFAR-10 содержит 50 000 обучающих и 10 000 тестовых изображений.

В проекте обучающая часть разделяется стратифицированно с фиксированным seed.

| Split | Изображений |
|---|---:|
| Train | 45 000 |
| Validation | 5 000 |
| Test | 10 000 |
| **Всего** | **60 000** |

Параметры по умолчанию:

```text
seed = 42
validation_size = 5000
```

Стратификация сохраняет распределение классов. При стандартном разбиении каждый класс представлен 4 500 изображениями train, 500 validation и 1 000 test.

Оригинальная тестовая выборка не изменяется.

### Ограничения

CIFAR-10 предназначен для учебных и исследовательских задач классификации изображений.

Изображения имеют низкое разрешение, поэтому результаты моделей на CIFAR-10 нельзя автоматически переносить на реальные изображения высокого разрешения.

При использовании датасета необходимо учитывать условия распространения исходного набора данных.

## Pipeline обработки данных

### Этап 1. Ingest

```bash
make ingest
```

Команда загружает официальный архив CIFAR-10 и сохраняет его в S3:

```text
s3://ml-datasets/raw/cifar-10-python.tar.gz
```

Raw-архив сохраняется без изменений.

Повторный ingest не перезаписывает существующий объект.

### Этап 2. Download

```bash
make download-raw
```

Команда скачивает raw-архив из S3 в:

```text
data/raw/cifar-10-python.tar.gz
```

Целостность проверяется по официальной MD5-сумме:

```text
c58f30108f718f92721af3b95e74349a
```

### Этап 3. Convert

```bash
make convert DATA_VERSION=v1
```

Из исходного архива формируются PNG-изображения и JSON-аннотации.

Локальный каталог:

```text
data/processed/cifar10/v1/
```

Для каждого изображения сохраняются идентификатор, имя файла, метка класса, название класса и SHA-256.

Python pickle используется только для обработки доверенного официального архива CIFAR-10.

### Этап 4. Split

```bash
make split DATA_VERSION=v1
```

Выполняется воспроизводимое стратифицированное разделение исходной обучающей выборки на train и validation.

Параметры можно изменить:

```bash
make split DATA_VERSION=v2 VAL_SIZE=5000 SEED=42
```

Перед запуском для новой версии необходимо выполнить конвертацию.

### Этап 5. Statistics

```bash
make statistics DATA_VERSION=v1
```

Рассчитываются среднее значение и стандартное отклонение RGB-каналов.

Статистики вычисляются **только по train**, чтобы избежать утечки информации из validation и test.

Пиксели нормализуются в диапазон [0, 1].

Для стандартной версии v1 получены:

| Канал | Mean | Std |
|---|---:|---:|
| R | 0.491840 | 0.247051 |
| G | 0.482541 | 0.243542 |
| B | 0.446820 | 0.261692 |

Используется стандартное отклонение генеральной совокупности (`ddof=0`).

Результат сохраняется в `stats.json`.

### Этап 6. Publish

```bash
make publish DATA_VERSION=v2
```

Команда загружает обработанные данные в S3 с указанной версией.

Загрузка PNG выполняется параллельно. По умолчанию используется 16 workers.

Публикуются:

- изображения train, validation и test;
- JSON-аннотации;
- статистики RGB;
- `manifest.json`.

Manifest содержит источник данных, размеры, контрольные суммы, количество изображений, параметры обработки и информацию о Git-коммите.

Manifest публикуется последним, после завершения загрузки остальных файлов.

Опубликованная версия не должна перезаписываться. Для новой обработки необходимо использовать новый идентификатор версии.

### Полный запуск

Для последовательного выполнения всех этапов после ingest:

```bash
make data DATA_VERSION=v2
```

Pipeline выполняет:

```text
download-raw
    |
    v
convert
    |
    v
split
    |
    v
statistics
    |
    v
publish
```

Команда `make data` предполагает, что RustFS запущен, бакет создан и raw-архив уже загружен через `make ingest`.

Для новой версии можно указать параметры:

```bash
make data DATA_VERSION=v2 VAL_SIZE=5000 SEED=42 WORKERS=16
```

Версия `v1` уже была опубликована в ходе разработки. Повторная публикация в тот же S3-префикс блокируется. Для нового полного запуска используйте ещё не опубликованную версию.

## Структура S3

```text
s3://ml-datasets/
├── raw/
│   └── cifar-10-python.tar.gz
└── processed/
    └── cifar10/
        └── v1/
            ├── images/
            │   ├── train/
            │   ├── val/
            │   └── test/
            ├── annotations/
            │   ├── train.json
            │   ├── val.json
            │   └── test.json
            ├── stats.json
            └── manifest.json
```

Изображения validation физически хранятся отдельно в S3, хотя локально они выбираются из исходного каталога `images/train` по JSON-аннотациям.

В S3 также может временно появляться служебный lock в `processed/cifar10/_locks/`. Он защищает публикацию версии от одновременной записи и удаляется после успешного завершения.

## Воспроизводимость и целостность

Для воспроизводимости обработки используются:

- фиксированный seed для train/validation;
- сохранение параметров обработки в manifest;
- контрольные суммы исходного архива и артефактов;
- версия обработанного датасета;
- Git commit и признак незакоммиченных изменений;
- фиксированные версии Python-зависимостей в `uv.lock`;
- закреплённые версии Docker-образов.

Контрольные суммы официального raw-архива:

```text
MD5:
c58f30108f718f92721af3b95e74349a

SHA-256:
6d958be074577803d12ecdefd02955f39262c83c16fe9348329d7fe0b5c001ce
```

Для максимально воспроизводимой публикации рекомендуется запускать pipeline из чистого Git working tree.

## Локальные данные и Git

Каталог `data/` используется для локальных raw- и processed-данных.

Сгенерированные изображения и архивы не должны коммититься в репозиторий.

Файл `.env` также исключён из Git.

В Git хранятся исходный код, конфигурации, lock-файлы зависимостей и документация.

```bash
uv run pre-commit run --all-files
```

## Git workflow

Разработка ведётся в отдельных feature-ветках.

Изменения в `main` вносятся через pull request.

Перед коммитом запускаются pre-commit проверки. GitHub Actions проверяет изменения в CI.

Рекомендуемый порядок:

1. Создать feature-ветку.
2. Внести изменения.
3. Выполнить `make check`.
4. Создать commit.
5. Отправить ветку в GitHub.
6. Создать pull request.
7. Убедиться, что CI завершился успешно.
